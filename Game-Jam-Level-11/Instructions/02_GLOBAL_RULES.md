# 02. Глобальные правила разработки

## ГЛОБАЛЬНОЕ ПРАВИЛО №1 — НИЧЕГО НЕ СОЗДАВАТЬ В РАНТАЙМЕ

**Вся структура игры, объекты, компоненты и интерфейс должны быть заранее подготовлены в Unity Editor и настраиваться через отдельные Prefab Assets / Prefab Variants и Inspector.**

Код во время игры отвечает за игровую логику и изменение состояния уже существующих объектов. Он не должен собирать сцену, создавать визуальные элементы или конструировать интерфейс.

Это обязательное архитектурное правило для всего проекта.

### Запрещено

- Вызывать Instantiate для игровых объектов, эффектов, текста, панелей или элементов UI.
- Вызывать Destroy для управления обычным игровым циклом.
- Создавать объекты через new GameObject, добавлять компоненты через AddComponent или строить иерархию сцены из кода.
- Создавать Canvas, Panel, Button, Text, Image, Layout Group и другие UI-компоненты программно.
- Добавлять кнопки, строки текста, иконки, полосы прогресса или другие элементы интерфейса в рантайме.
- Искать критически важные ссылки глобально во время игры через FindObjectOfType, FindFirstObjectByType, GameObject.Find и аналоги.
- Использовать процедурную генерацию объектов как замену заранее подготовленным префабам.

### Обязательно

1. Каждый повторно используемый игровой объект оформлять отдельным Prefab.
2. Настройки объектов и баланс выносить в сериализуемые поля Inspector. Не зашивать баланс в код без необходимости.
3. Все обязательные ссылки назначать заранее через Inspector. При отсутствии обязательной ссылки выдавать понятную ошибку в Editor/Console, а не пытаться незаметно найти или создать замену в рантайме.
4. Если нужно несколько одинаковых объектов, заранее размещать их экземпляры в сцене или заранее подготовленном родительском объекте.
5. Если объект должен временно исчезать, разрешено переключать состояние уже существующего объекта через SetActive или включение компонента. Это изменение состояния, а не создание объекта.
6. Новые варианты внешнего вида создавать как Prefab Variants, а не как дополнительные ветки условий в коде.

## Особенно строго — UI

Интерфейс должен быть полностью собран в редакторе и настраиваться отдельно от игровой логики.

Рекомендуемые самостоятельные префабы:

- **UI_HUD.prefab** — запас огня, таймер, счёт и индикатор предупреждения о ветре.
- **UI_StartPanel.prefab** — стартовый экран и подсказки управления.
- **UI_ResultPanel.prefab** — победа/поражение, итоговое время и кнопка Retry.
- **UI_PausePanel.prefab** — только если основная игра уже готова.

У каждого префаба собственная иерархия, размеры, шрифты, цвета, анимации и ссылки на кнопки. Всё это редактируется в Inspector/Prefab Mode.

**Никакого программного создания интерфейса.** Не создавать Canvas или дочерние элементы из скриптов. Все нужные панели заранее присутствуют в сцене, изначально включены или выключены согласно стартовому состоянию. Код только обновляет значения существующих полей и переключает уже существующие панели.

## Пулы без Instantiate

Если нужны временные объекты (например, топливо), использовать заранее размещённые экземпляры:

- Разместить все точки топлива в сцене вручную.
- После подбора выключать конкретный экземпляр.
- После таймера снова включать тот же экземпляр.
- Для каждого экземпляра заранее назначить его позицию и параметры.

Не создавать новый pickup при каждом появлении топлива. Не делать бесконечную генерацию объектов.

## Что разрешено в рантайме

Разрешена логика, которая меняет состояние уже созданных объектов:

- движение игрока;
- расчёт запаса огня, таймера и счёта;
- проверка столкновений и триггеров;
- включение/выключение заранее созданных точек топлива и UI-панелей;
- изменение радиуса/интенсивности заранее назначенного Light2D;
- изменение текста и заполнения заранее созданных UI-компонентов;
- воспроизведение заранее назначенных AudioSource и Animator;
- переключение игровых состояний.

Иными словами: **не создавать структуру, а управлять уже созданной структурой.**

## Правило настройки

Если дизайнер должен иметь возможность изменить число, цвет, скорость, размер, текст, ссылку, звук или внешний вид — это должно быть доступно в Inspector через serialized field, отдельный Prefab или Prefab Variant.

Не вводить глобальные скрытые настройки и магические константы без причины.

## Проверка перед коммитом

- [ ] Нет runtime Instantiate, new GameObject, AddComponent для игрового контента/UI.
- [ ] Нет динамического построения Canvas или иерархии UI.
- [ ] Все ссылки на объекты и UI назначены через Inspector.
- [ ] Все повторяющиеся объекты заранее размещены или заранее подготовлены.
- [ ] Баланс можно менять в Inspector.
- [ ] Изменения внешнего вида можно сделать через Prefab Mode без правки кода.
