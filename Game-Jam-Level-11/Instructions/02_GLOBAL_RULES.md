# 02. Глобальные правила разработки

## ГЛОБАЛЬНОЕ ПРАВИЛО №1 — НИЧЕГО НЕ СОЗДАВАТЬ И НЕ СОБИРАТЬ В РАНТАЙМЕ

**Вся структура игры, игровые объекты, компоненты, визуальные эффекты и интерфейс заранее создаются в Unity Editor. Каждый настраиваемый элемент должен быть отдельным Prefab Asset или Prefab Variant и редактироваться через Prefab Mode / Inspector.**

Под «ничего не делать в рантайме» здесь понимается: не создавать, не собирать и не перестраивать объекты или UI во время игры. Рантайм-код может управлять логикой и состоянием уже существующих объектов, но не должен конструировать содержимое сцены.

Это обязательное архитектурное правило для всего проекта.

### Запрещено

- Вызывать Instantiate для игровых объектов, эффектов, текста, панелей или элементов UI.
- Вызывать Destroy для управления обычным игровым циклом или повторным появлением объектов.
- Создавать объекты через new GameObject, добавлять компоненты через AddComponent или строить иерархию сцены из кода.
- Создавать Canvas, Panel, Button, Text, Image, Layout Group и другие UI-компоненты программно.
- Добавлять кнопки, строки текста, иконки, полосы прогресса, уведомления, подсказки или другие элементы интерфейса в рантайме.
- Создавать UI-строки или элементы списков по запросу игры. Все возможные элементы должны существовать заранее.
- Искать критически важные ссылки глобально во время игры через FindObjectOfType, FindFirstObjectByType, GameObject.Find и аналоги.
- Использовать процедурную генерацию объектов как замену заранее подготовленным префабам.
- Создавать визуальные эффекты, звуковые источники или анимационные объекты на лету.

### Обязательно

1. Каждый повторно используемый игровой объект оформлять отдельным Prefab.
2. Каждый самостоятельный экран или крупный элемент интерфейса оформлять отдельным Prefab. При необходимости мелкие элементы HUD также делать вложенными префабами.
3. Настройки объектов, визуальный вид и баланс выносить в сериализуемые поля Inspector. Не зашивать баланс в код без необходимости.
4. Все обязательные ссылки назначать заранее через Inspector. При отсутствии обязательной ссылки выдавать понятную ошибку в Editor/Console, а не пытаться незаметно найти или создать замену в рантайме.
5. Все экземпляры, нужные на уровне, заранее размещать в сцене как prefab instances.
6. Если нужно несколько одинаковых объектов, размещать нужное количество экземпляров заранее. Не создавать недостающие экземпляры из кода.
7. Если объект должен временно исчезать, разрешено переключать состояние уже существующего объекта через SetActive или включение компонента. Это изменение состояния, а не создание объекта.
8. Новые варианты внешнего вида создавать как Prefab Variants, а не как дополнительные ветки условий в коде.
9. Если дизайнер должен менять параметр, он должен быть доступен на соответствующем Prefab через Inspector.

## Особенно строго — UI

Интерфейс должен быть полностью собран в редакторе и настраиваться отдельно от игровой логики.

Рекомендуемая структура:

- **UI_HUD.prefab** — корневой Canvas, CanvasScaler и GraphicRaycaster; внутри заранее размещены вложенные префабы HUD.
- **UI_FlameMeter.prefab** — иконка огня, полоска запаса и визуальные состояния.
- **UI_Timer.prefab** — таймер матча.
- **UI_WindWarning.prefab** — заранее созданный индикатор предупреждения о ветре.
- **UI_StartPanel.prefab** — стартовый экран, цель и подсказки управления.
- **UI_ResultPanel.prefab** — результат, время и кнопка Retry.
- **UI_PausePanel.prefab** — только если основная игра уже готова.

Каждый префаб имеет собственную иерархию, размеры, anchors, шрифты, цвета, анимации и ссылки на компоненты. Всё это редактируется в Inspector/Prefab Mode.

**Никакого программного создания интерфейса.** Все панели и элементы должны быть заранее размещены в сцене внутри Canvas. Они изначально включены или выключены согласно стартовому состоянию. Код только обновляет значения существующих Text / TMP_Text / Slider / Image и переключает уже существующие панели.

Если состояние UI меняется, использовать заранее назначенные ссылки. Например, при победе включить существующий UI_ResultPanel и изменить текст заранее размещённого поля результата. Не создавать новую панель, кнопку или текст.

Если количество элементов заранее известно, подготовить именно столько визуальных слотов в префабе. Не строить динамические списки.

## Пулы без Instantiate

Если нужны временные объекты, например топливо:

- Разместить все точки топлива в сцене вручную.
- Для каждой точки заранее назначить позицию и параметры.
- После подбора выключать конкретный экземпляр.
- После cooldown снова включать тот же экземпляр.
- Не создавать новый pickup при каждом появлении топлива.
- Не делать бесконечную генерацию объектов.

То же правило действует для временных эффектов: заранее подготовить нужное число объектов и менять состояние существующих.

## Что разрешено в рантайме

Разрешена логика, которая меняет состояние уже созданных объектов:

- движение игрока и расчёт столкновений;
- расчёт запаса огня, таймера и счёта;
- проверка триггеров и получение топлива;
- включение/выключение заранее созданных точек топлива и UI-панелей;
- изменение радиуса и интенсивности заранее назначенного Light2D;
- изменение текста и заполнения заранее созданных UI-компонентов;
- воспроизведение заранее назначенных AudioSource и Animator;
- переключение игровых состояний;
- перезапуск значений уже существующих объектов.

Иными словами: **не создавать структуру, а управлять уже созданной структурой.**

## Правило настройки

Если дизайнер должен иметь возможность изменить число, цвет, скорость, размер, текст, ссылку, звук или внешний вид — это должно быть доступно в Inspector через serialized field, отдельный Prefab или Prefab Variant.

Не вводить глобальные скрытые настройки и магические константы без причины. Не заставлять пользователя менять код для обычной настройки баланса, UI или визуального вида.

## ГЛОБАЛЬНОЕ ПРАВИЛО №2 — ОТВЕЧАТЬ КОРОТКО И ПО ДЕЛУ

**Пользователь не должен разбирать длинные отчёты, чтобы понять, что от него требуется. Сначала сообщай конкретный запрос к пользователю.**

Каждый ответ пользователю оформляй так:

1. **От тебя нужно:** одно конкретное действие, решение или ответ. Если действий не требуется, прямо напиши: «От тебя ничего не требуется».
2. **Что сделано / что будет сделано:** максимум 1–3 коротких пункта, только существенный результат.
3. **Проблема или блокер:** укажи только если действительно мешает продолжать; напиши, что именно нужно для разблокировки.

### Ограничения по длине и стилю

- Начинай с сути. Не начинай с длинного приветствия, пересказа задачи или описания своего плана.
- По умолчанию пиши не более 3–5 коротких предложений. Подробности, объяснения и технические рассуждения давай только по запросу или когда без них нельзя безопасно выполнить задачу.
- Не присылай пользователю длинные логи, полный лист изменений, внутренние рассуждения, повтор уже известного контекста или список очевидных действий.
- Не перечисляй варианты, если от пользователя требуется выбрать только один параметр. Сразу предложи лучший вариант и задай один короткий вопрос, если без ответа нельзя продолжить.
- Если нужно действие в Unity Editor, назови точный объект, файл или вкладку и конкретное действие.
- Если пользователь должен что-то проверить, укажи конкретно что проверить и какой результат ожидается.
- Если действие не требуется, не придумывай вопрос или дополнительную задачу ради продолжения диалога.
- Не утверждай, что файл изменён, код создан, тест пройден, Unity-сцена открыта или сборка проверена, если это фактически не подтверждено.
- Не сокращай критически важные предупреждения, ошибки, ограничения или шаги, без которых пользователь может сломать проект.
- Подробный технический отчёт предоставляй только по прямому запросу пользователя.

### Обязательный формат отчёта после задачи

**От тебя нужно:** [конкретный шаг пользователя / «ничего»].

**Готово:** [короткий фактический результат].

**Блокер:** [только если есть; иначе строку не добавлять].

## Проверка перед коммитом

- [ ] Нет runtime Instantiate, new GameObject, AddComponent или динамического построения Unity-объектов.
- [ ] Нет динамического построения Canvas или иерархии UI.
- [ ] Все ссылки на объекты и UI назначены через Inspector.
- [ ] Все повторяющиеся объекты заранее размещены или заранее подготовлены.
- [ ] Баланс можно менять в Inspector.
- [ ] Внешний вид интерфейса можно изменить через Prefab Mode без правки кода.
- [ ] Новые UI-элементы не создаются из скриптов.
- [ ] Ответ пользователю начинается с конкретного действия, которое от него требуется, или с фразы «От тебя ничего не требуется».
- [ ] Ответ не перегружен подробностями, которые пользователь не запрашивал.
